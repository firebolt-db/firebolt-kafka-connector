# E2E Testing Framework for Firebolt Kafka Connector

## Summary

Build a comprehensive E2E testing framework that validates the Firebolt Kafka Connector across message types, delivery semantics, and ingestion modes — with throughput benchmarking, automated PR reporting, and chaos/exactly-once stress testing.

The framework builds on the existing `LoadTest` infrastructure in `src/integrationTest/java/com/firebolt/kafka/connect/load/` and the Docker Compose setup in `src/integrationTest/docker/`.

## Goals

1. **Multi-message-type E2E tests** — JSON, Avro, Protobuf with configurable parameters (exactly-once delivery, binary upload mode)
2. **Throughput benchmarking** — configurable-duration pressure tests (~2 min default) with metrics collection
3. **GitHub PR performance reporting** — automated PR comments with throughput results in a formatted table
4. **Chaos/exactly-once stress testing** — continuous data injection with system component kills, validated via checksum comparison against `generate_series(1, N)`

## Design

### 1. Core E2E Test Framework

**Configuration Matrix:**
Each E2E test scenario is defined by a combination of:

- **Message type**: JSON, Avro, Protobuf
- **Delivery semantics**: at-least-once (default), exactly-once
- **Ingestion mode**: SQL (default), binary (Parquet upload)

This gives us a 3 × 2 × 2 = 12 configuration matrix. Tests should be parameterized so adding a new message type or config option doesn't require new test classes.

**Test Data:**

- Use a consistent schema across all message types: `id` (long), `name` (string), `value` (double), `timestamp` (timestamp)
- Data generators produce records with sequential IDs for deterministic validation
- For throughput tests, configurable record size (pad `name` field)

**Location:** `src/integrationTest/java/com/firebolt/kafka/connect/e2e/`

**Key Classes:**

- `E2ETestConfig` — configuration POJO for a test scenario (message type, delivery mode, ingestion type, duration, record count, etc.)
- `E2ETestHarness` — orchestrates: setup Kafka topic, deploy connector config, produce messages, wait for ingestion, validate results
- `MessageProducer` — generic producer that serializes test records in the configured format (JSON/Avro/Protobuf)
- `FireboltValidator` — connects to Firebolt via JDBC, validates record counts, checksums, and schema correctness

### 2. Message Type E2E Tests

Parameterized JUnit 5 tests that exercise each cell of the configuration matrix:

```java
@ParameterizedTest
@MethodSource("configMatrix")
void testIngestion(E2ETestConfig config) {
    harness.setup(config);
    harness.produceRecords(config.recordCount());
    harness.waitForIngestion();
    harness.validateRecordCount();
    harness.validateDataIntegrity();
}
```

Each test:

1. Creates a Kafka topic
2. Deploys the connector with the appropriate config
3. Produces N records in the specified format
4. Waits for ingestion to complete (poll Firebolt row count with timeout)
5. Validates: correct record count, data integrity (spot-check values), schema correctness

### 3. Throughput Benchmarking

**Approach:**

- Produce records continuously for a configurable duration (default: 2 minutes)
- Track: total records produced, total records ingested, bytes produced, elapsed time
- Calculate: records/sec, MB/sec, end-to-end latency (producer timestamp to Firebolt availability)

**Metrics collected:**

| Metric | Description |
| --- | --- |
| `records_produced` | Total records sent to Kafka |
| `records_ingested` | Total records landed in Firebolt |
| `throughput_records_sec` | Records per second |
| `throughput_mb_sec` | Megabytes per second |
| `avg_record_size_bytes` | Average record size |
| `duration_seconds` | Actual test duration |
| `config` | Full test configuration |

**Implementation:**

- `ThroughputBenchmark` — runs the benchmark, collects metrics, produces a `BenchmarkResult`
- `BenchmarkResult` — structured result object with all metrics
- `BenchmarkReportGenerator` — formats results as Markdown for PR comments

### 4. GitHub PR Reporting

**Approach:**

- After throughput benchmarks complete, generate a Markdown report
- Post as a PR comment via the GitHub API (using `GITHUB_TOKEN` from CI)
- Include a summary table with all benchmark results

**Report format:**

```markdown
## Kafka Connector Performance Report

| Config | Records/sec | MB/sec | Records | Duration |
|---|---|---|---|---|
| JSON / at-least-once / SQL | 12,450 | 3.2 | 1,494,000 | 120s |
| Avro / exactly-once / binary | 8,230 | 2.1 | 987,600 | 120s |
| ... | ... | ... | ... | ... |

_Generated by E2E throughput benchmarks on commit `abc1234`_
```

**Implementation:**

- `GitHubPRReporter` — uses GitHub API to post/update PR comments
- Triggered via a Gradle task or CI workflow step
- Uses a comment marker to update existing comments rather than creating duplicates

### 5. Chaos / Exactly-Once Stress Testing

**Scenario:**

1. Deploy connector with `exactlyOnce=true`
2. Start producing records with sequential keys `1, 2, 3, ..., N`
3. While producing, periodically kill and restart system components:
   - Firebolt Core container
   - Kafka broker
   - Kafka Connect worker
   - Schema Registry
4. After all records are produced and the system recovers:
   - Wait for all records to be ingested
   - Validate: `SELECT checksum(key_column) FROM target_table` equals `SELECT checksum(x) FROM generate_series(1, N) r(x)` in Firebolt
   - Also validate: `SELECT COUNT(DISTINCT key_column) = N`

**Fault Injection:**

- `ChaosOrchestrator` — controls timing and selection of component kills
- Uses Docker/Testcontainers API to stop/start containers
- Configurable: kill interval, kill duration, which components to target
- Random selection with configurable seed for reproducibility

**Validation:**

- Checksum comparison is the primary correctness check
- Also validate no duplicates (exactly N distinct keys)
- Timeout-based recovery detection (wait for connector to catch up after each fault)

**Key Classes:**

- `ChaosOrchestrator` — fault injection controller
- `ExactlyOnceStressTest` — the main test
- `ContainerController` — wraps Docker API for stop/start operations
- `ChecksumValidator` — executes the checksum comparison query

## Infrastructure

### Docker Compose

Extends existing compose files in `src/integrationTest/docker/`. May need:

- Health checks on all containers for chaos testing recovery detection
- Volume mounts for the connector plugin (already exists)

### CI Integration

- New GitHub Actions workflow: `.github/workflows/e2e-tests.yml`
- Triggered on PR (throughput benchmarks) and on schedule (chaos tests)
- Posts PR comments with performance results
- Chaos tests may run on a longer schedule (nightly) due to duration

### Dependencies

- Protobuf support: `com.google.protobuf:protobuf-java` + Confluent Protobuf converter
- GitHub API client: `org.kohsuke:github-api` (for PR comments)
- No new Docker images needed — uses existing Confluent and Firebolt images
